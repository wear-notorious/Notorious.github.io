## Reconciliation

`Engine.reconcile(order_id, token, candidate_paypal_id=None)` and the local `POST /api/orders/{id}/reconcile` endpoint perform **read-only** PayPal lookups; they never create, approve, or capture. Authentication uses the same bearer token as the order. The POST body is `{}` or `{"candidatePayPalOrderId":"..."}`. No reconciliation calls are made automatically at startup.

- CREATE_UNKNOWN or CREATE_IN_PROGRESS: supply an independently recovered PayPal order ID. The engine checks order ID, custom ID, merchant, currency, exact amount, one purchase unit, eligible unpaid status and absence of captures. On a match it records AWAITING_APPROVAL. Missing ID, lookup failure, mismatch, or a reused ID stays unresolved. PayPal cannot be queried here by the locally generated request key: never infer an order ID or repeat creation automatically.
- CAPTURE_UNKNOWN or CAPTURE_IN_PROGRESS: GET order and GET capture; only verified COMPLETED evidence transitions to PAID_PENDING_SHEET. Missing, incomplete, refunded, mismatched, or unavailable evidence stays pending. APPROVED alone is not evidence of capture failure and never triggers another capture.
- SHEET_IN_PROGRESS: transition to PAID_PENDING_SHEET for a separately requested idempotent sync to the reserved row; a verified reread is required before CONFIRMED.
- OS file locks keyed by the request hash are held during create, capture, sync and reconcile, including their network calls. A concurrent operation returns PENDING; a terminated process releases the lock, while SQLite preserves the state. All processes must run this exact version, use the same canonical DB path and lock directory on the same shared local filesystem. Do not delete lock files while the service is active. Multiple independent hosts/filesystems, NFS, older code that bypasses the lock, or copies of the database are unsupported. A remote operation might still be processing after a process dies; read-only reconciliation never treats an unresolved state as permission to resend.
- To recover a stuck reconciliation after another crash, retry the same read-only reconciliation. Non-unique PayPal order and capture IDs are rejected by SQLite constraints. Any SQLite conflict or missing evidence leaves the previous state unchanged.

## Secure connection procedure — prepare only

1. Confirm the existing spreadsheet is **NOTORIOUS TEST** and record its ID privately. Create a separate, initially empty tab named exactly `SandboxBackendOrders` with an owner-controlled header in A1:E1: order ID, PayPal order ID, capture ID, USD amount, snapshot. Do not change or write to `Orders`. Do not connect the server until permissions and backup are reviewed.
2. Use a dedicated test identity and an OAuth mechanism with refresh capability and the narrowest viable per-file authorization. Google Sheets scopes apply to an entire spreadsheet, not an individual tab; they cannot enforce access only to this tab. `drive.file` may be appropriate when the file is explicitly made available to the app. Verify the exact grant and consider protecting `Orders` or a separate test spreadsheet for stronger isolation. Never assume the adapter's tab name is an authorization boundary.
3. Enable the Sheets API and arrange authorized access to that one test file through an approved identity flow. Granting a new service account or app access changes permissions and must be explicitly reviewed. Do not place OAuth tokens or private keys in GitHub, browser code, logs, or chat. The local adapter now supports renewable Application Default Credentials (ADC) through google-auth. ADC is not configured, authorized or tested against Google. Its effective scope is determined by the actual grant, not only by the scope requested by code. Use an explicitly reviewed per-file grant and prefer keyless credentials. Local ADC user files can contain long-lived refresh credentials and require restricted access.
4. Configure `TEST_SPREADSHEET_ID` to the verified TEST file; the adapter hardcodes `SandboxBackendOrders` and refuses other tab names. Assign a private persistent local SQLite path with restricted filesystem permissions. Back up and restore database and dedicated tab together. Never manually sort, insert or reuse rows in the dedicated tab: reserved row numbers are persisted in SQLite.
5. Before any write, verify the tab is empty apart from its header, the account and file ID are correct, and the backend is the only writer. In a separately authorized isolated test, write a synthetic order to a reserved row, read back A:E and repeat the same sync after a simulated timeout; confirm exactly one matching row and that `Orders` is unchanged. This end-to-end test has **not** been performed.

Google references: https://developers.google.com/workspace/sheets/api/scopes and https://developers.google.com/workspace/sheets/api/reference/rest/v4/spreadsheets.values/update

## Remaining limitations

- Real PayPal COMPLETED/capture response shapes, refund handling, real Sheets concurrency and full end-to-end recovery are unverified. A lost create ID may require manual investigation; some cases cannot be recovered safely with the available API evidence.
- Catalog and conversion rate are test configuration, not synchronized with Products. The fixed rate needs review.
- The Google ADC provider refreshes invalid credentials, but its dependency, actual granted scopes, and real Sheets access have not been tested; no real Sheets connection or dedicated tab has been established. Sheets sync assumes exclusive management of an empty dedicated tab and that DB and tab are backed up together.
- The authenticated HTTP API is local-only: TLS, hardened authentication and authorization, rate limiting, token lifecycle, CSRF/origin policy, data encryption and independent security review remain necessary before exposure. PII is stored unencrypted in the local SQLite database and test sheet.
- Configure `NOTORIOUS_ENV=TEST`, `TEST_DB_PATH`, `TEST_CATALOG_JSON`, `TEST_MAD_TO_USD_RATE`, `TEST_PAYPAL_MERCHANT_ID`, `TEST_PAYPAL_CLIENT_ID`, `TEST_PAYPAL_SECRET`, and `TEST_SPREADSHEET_ID` privately; configure ADC separately only after authorization. Never enable `TEST_CAPTURE_ENABLED` without explicit authorization. No service is started by tests.

## Credential preparation (not authorized or connected)

`google_auth_provider.py` uses Application Default Credentials and `google-auth` with `drive.file` requested, refreshes credentials when invalid, and never logs them. Install and review google-auth with its requests transport in the eventual isolated environment; no dependency was installed or Google login performed during offline tests. ADC can select existing credentials from multiple sources and existing user scopes may be broader; explicitly verify the selected identity, actual scopes and access to the single new test file before granting or using access. This code does not grant access or restrict Google permissions by itself. Prefer a keyless attached identity or federation where feasible. Creation of an OAuth client, service identity, or sharing the file requires separate authorization.
